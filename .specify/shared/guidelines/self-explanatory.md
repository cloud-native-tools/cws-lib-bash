# 不言自明（Self-explanatory）— 实践指南

> **概念 owner**：`.specify/shared/definitions/self-explanatory-definitions.md`。本文件只拥有**实践方法**，不重述概念定义与判据阈值。
>
> **强制力**：见概念定义 §5；本指南不重复该值。
>
> **Status**: confirmed at exit gate — 2026-11-04.

## 1. 何时应用

起点不是“先选一个维度”，而是从上下文识别**用户是否需要一套更明确的信息系统**。触发方式有两种：

- 用户主动指出某个名称、路径或结构需要优化；
- 在“优化”“改进”“当前实现不满足要求”这类请求中，由流程把本实践作为候选提示给用户。

## 2. 操作步骤

1. **识别用户需要的信息**：用户要在入口处完成什么筛选、排序或判断？
2. **确定信息维度**：把用户需要的那一个维度写清楚，不先枚举其他维度。
3. **检查可达性**：按概念定义 §2 的上下限判断，本次改造是否达到可支持执行的下限？
4. **确定真源与投影**：如果该维度已有真源（例如 `goal.md` 的 frontmatter `status`），保持真源不变，把名称/路径作为投影；不得让路径成为第二真源。
5. **按维度增加顺序执行**：顺序的 owner 是概念定义 §7；本步骤只负责执行，不重述顺序。
6. **小步落地并验证**：改动后确认下限可达、只增加了一个维度、命名来源规则未被绕过。
7. **及时止损**：如果改动没有带来用户侧的信息收益，或引入了维度堆叠，回退该维度，不继续叠加。

## 3. 维度过多的护栏

- 执行概念定义 §7 的“每次最多一个维度”；需要多个维度时拆成多次改动。
- 如果下限已经满足，不再为了“更直观”增加新维度。
- 如果新维度只是重复已有真源，不增加，改为改善查询或展示。
- 如果新增维度要求用户同时理解多个新分类，停止并重新评估需求。

## 4. 投影的维护

- 投影的维护要求见概念定义 §6；操作上：
- 用户看到投影与真源不一致时，以真源为准，运行调协；不得手工改路径来“修正”状态。
- 调协机制缺失时，先补调协，再启用投影。

## 5. 示例：goal 状态目录（仅示例）

`.specify/goal/<goal-slug>/` 在 `ls` 下只显示 slug；若用户需要一眼看出状态，可把 status 维度提升为路径层级 `.specify/goal/<status>/<goal-slug>/`。status 的真源仍是 `goal.md` 的 frontmatter，路径由调协机制维护。

该改造只是本概念的一个示例；本仓是否执行、何时执行，作为后续项交由 `/speckit.todo` 记录，不在本指南中强制。

## 6. 与最佳实践优化工作流的关系

本指南是“不言自明”这一项最佳实践的实践 owner。承载最佳实践的优化工作流是 `.specify/shared/workflow/best-practice-optimization.md`；每次 `/speckit.improve` 都参考该工作流，其他 `/speckit.*` 命令在输出或集成最佳实践时也应用它。

本指南不定义该工作流的上下文分析、最佳实践查找、选择与输出映射；这些由工作流 owner 负责。

## 7. 反模式

- 为了“不言自明”而堆叠维度，导致名称、路径或结构难以阅读。
- 把路径当作可独立编辑的第二真源。
- 用程序视角的可读性替代用户视角的信息可达性。
- 把某个具体布局（例如 goal 的 status 目录）规定为所有项目的强制标准。
- 在没有实时性要求时强行逐写同步投影，增加不必要的成本。
- 在没有具体用户信息需求时做预防性改造（“先把结构改得更自解释”）；目的性不足，不做。

## 8. 目的性约束的操作检查

目的性约束的概念 owner 是概念定义 §3；本指南只给操作检查：

- 每次改造先写出它服务的具体筛选、排序或判断需求；写不出就不做。
- 没有具体需求的预防性改造不进入调协。
- 可达性按概念定义 §2 判断，不额外要求所有信息公开可见。
- 投影按概念定义 §6 维护，不额外要求实时同步。

## 9. 既有结构的迁移（reconcile 模式）

- 既有结构**逐步迁移**，不一次性重排。
- 使用 reconcile pattern（`.specify/shared/patterns/reconcile-pattern.md`）；本指南只补充本实践的迁移规则，不重定义该模式。
- **粒度区分**：概念定义 §7 的“每次最多一个维度”是**优化任务**层面的约束，任务目标就是增加一个维度；本节描述的是**实现该目标**的过程——通过多次调协，每次生成一个具体的、向目标靠近的动作，直到该维度的改造完成。调协动作与维度不是同一粒度，调协可以分多步完成同一个维度。
- **新结构**：直接执行。
- **既有结构**：先评估影响，再由用户决定是否执行。
- **影响评估的内容**：对于文件、路径和变量名的修改，必须找出所有引用这些名称的代码或流程；评估改造工作量；评估向前兼容性（旧名称、外部消费者、迁移过渡）。评估结果以可决策的形式呈现给用户。
- 每次调协重复上述步骤；调协后的投影按概念定义 §6 维护。
- 停止条件：概念定义 §3 的目的性约束不成立、概念定义 §2 的下限已满足、影响评估显示成本大于收益，或用户决定不做。

## 10. 验收与样例积累框架

验收样例在逐步实践中积累；当前不固化正例/反例清单，只提供记录框架。每次实践按以下字段记录一条：

| 字段 | 内容 |
|------|------|
| 用户信息需求 | 用户要在入口处完成的筛选、排序或判断 |
| 增加的维度 | 本次加入名称、路径或结构的单一维度 |
| 可达性 | 按概念定义 §2 记录本次达到的上限或下限 |
| 引用面 | 受影响的文件、路径、变量及其引用 |
| 影响评估 | 改造工作量、向前兼容性、用户决策 |
| 结果 | 合格 / 不合格 / 不值得做 / 已回退 |
| 备注 | 上下文、止损原因、后续动作 |

§5 的 goal 示例可以作为第一条记录的样例；随着实践增加，本表累积真实案例，而不是预先编造正反例。
